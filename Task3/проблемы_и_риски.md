# Task 3. Анализ проблем и рисков: переход на Event-Driven

## Контекст

Сейчас `core-app` и `ins-comp-settlement` получают данные о продуктах/тарифах через синхронный REST к `ins-product-aggregator`. Агрегатор при каждом вызове опрашивает все страховые компании (5, скоро +5), собирает ответ и возвращает его в том же запросе.

Локальные реплики данных:
- `core-app` обновляет реплику раз в 15 минут;
- `ins-comp-settlement` — раз в сутки (ночью).

Дополнительно `ins-comp-settlement` раз в сутки тянет из `core-app` все оформленные за день страховки по REST.

## Проблемы текущей архитектуры

### 1. Синхронный fan-out к страховым компаниям
При каждом запросе к `ins-product-aggregator` выполняется N внешних вызовов (сейчас 5, скоро 10). Латентность ответа = max(латентностей СК) + агрегация. Рост числа партнёров линейно ухудшает время ответа и вероятность таймаута.

### 2. Каскадные ошибки и нестабильность
Ошибки/задержки API одной СК портят весь синхронный ответ агрегатора. Это проявляется как сбои обновления локальных реплик в `core-app` / `ins-comp-settlement` и как деградация UX/B2B API.

### 3. Polling локальных реплик
Периодический pull (15 мин / 1 сутки) создаёт:
- окно устаревания данных (до 15 минут / до суток);
- лишнюю нагрузку даже когда продукты не менялись;
- пики нагрузки в моменты опроса (особенно ночной batch у settlement).

### 4. Жёсткая связность batch-взаимодействия settlement ↔ core-app
Суточный REST «забери все полисы за день» — пакетная точка отказа: если `core-app` недоступен ночью, реестр взаиморасчётов срывается. Нет естественного повторного потребления событий.

### 5. Дублирование логики согласованности
Два сервиса независимо синхронизируют одни и те же продукты разными расписаниями → разные версии данных в системе в один момент времени (рассинхрон реплик).

## Риски при росте нагрузки и числа СК (до 10)

| Риск | Описание | Влияние |
|------|----------|---------|
| R1. Рост латентности агрегации | 10 СК вместо 5 → выше p95/p99 ответа aggregator | Падение NPS, нарушение SLA B2B |
| R2. Усиление каскадных отказов | Больше внешних зависимостей в одном sync-запросе | Частые сбои обновления реплик |
| R3. Amplification нагрузки | Polling × рост пользователей × рост СК | Перегрузка aggregator и внешних API СК |
| R4. Срыв суточных реестров | Рост объёма оформленных полисов делает nightly REST-выгрузку тяжёлой и хрупкой | Финансовые/операционные потери settlement |
| R5. Рассинхрон тарифов | Разные TTL реплик при частых изменениях продуктов | Неверные предложения клиентам / ошибки расчётов |
| R6. Невозможность горизонтально масштабировать «чтение продуктов» | Все читатели бьют в один sync-путь | Узкое горлышко роста |

## Выводы для целевой архитектуры

1. Сохранить декомпозицию сервисов (`core-app`, `client-info`, `ins-product-aggregator`, `ins-comp-settlement`).
2. Перевести на **Event Streaming** взаимодействия, где сейчас polling / batch REST:
   - публикация обновлений продуктов/тарифов из `ins-product-aggregator`;
   - потребление этих событий в `core-app` и `ins-comp-settlement` (локальные реплики обновляются push-ом);
   - публикация событий «полис оформлен» из `core-app` для `ins-comp-settlement` вместо nightly REST.
3. Оставить REST там, где нужен синхронный запрос-ответ (web/B2B к `core-app`, вызовы к СК при online-оформлении — по необходимости).
4. Применить паттерн **Transactional Outbox** (см. схему) для атомарной записи бизнес-данных и исходящих событий, чтобы не терять события при сбоях после commit в БД.
